## Proposed architecture

1. Portal authenticates its user and generates a signed launch link valid for roughly five minutes.
2. The dashboard's Next.js server verifies the signed client/time/scope claims.
3. The dashboard issues its own protected HttpOnly session cookie with a proposed fixed two-hour lifetime.
4. Server configuration maps the verified client ID to that client's upstream API key.
5. The upstream API enforces ownership of the requested test; the dashboard returns only permitted analytics data.

No additional login system or database is inherently required. Exact scope and signing format remain to be confirmed with Viktor. Five-minute launch replay and delayed individual revocation are explicit tradeoffs to agree, not assumed approvals.

## Testing with access only to their deployed platform

Their backend source and a local copy of their Portal are not needed. Work in three stages:

### 1. Local dashboard with fixtures

Build sanitized API fixtures and a development-only script that signs localhost launch links using a dummy secret. Exercise signature rejection, session cookies/expiry, dataset mapping, navigation, mock client isolation, and stale-data cleanup locally. Keep the generator outside public application routes and prevent dummy credentials from being accepted in production. Use localhost HTTPS where needed to verify production Secure-cookie behavior.

This stage can begin without real credentials. It verifies our implementation, not the deployed Portal or API.

### 2. Local dashboard against deployed QA API

Our local Next.js server makes outgoing authenticated requests to the deployed QA API. The dashboard does not need to be deployed for this, provided the API is reachable from the developer's connection and has no additional network restrictions.

Use each QA client's key to fetch its own test. Then request Client B's test with Client A's key and verify the documented denial. Test the dashboard session-to-key selection independently using locally generated launch links in the development environment. A successful local simulator test does not establish that Viktor's real Portal signing code matches; use his fixed test vector and later the real handoff to prove that.

### 3. Stable deployed preview and actual Portal button

Deploy one preview after local auth and mapping work. Agree a stable callback/launch URL with Viktor, configure the real QA launch secret and client key map in the preview, and have the Portal's Open Dashboard button point there.

Later preview updates should retain the agreed launch URL. This stage requires Portal-team cooperation; it is not required for every local change.
